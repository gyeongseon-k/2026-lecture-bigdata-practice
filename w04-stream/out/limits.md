# Task 2 — 정확한 집계와 Flajolet-Martin의 한계 비교

## 측정 방법

tracemalloc을 켜면 메모리를 추적하는 비용 때문에 실행 시간이 약 4배 늘어났다(n=100,000에서 0.09초 → 0.34초, n=25,600,000에서 26.29초 → 105.52초). 그래서 시간과 메모리를 따로 측정했다. `limits.json`에서 `traced: true`인 행은 메모리 비교에, `traced: false`인 행은 시간 비교에 사용했다.

메모리는 두 가지를 구분했다. tracemalloc 값은 파이썬 객체가 요청한 메모리이고, RSS는 운영체제가 프로세스에 실제로 내준 메모리다. 두 방식의 메모리 비교(A3, A4)에는 tracemalloc 값을, 내 컴퓨터의 한계 판단(A2)에는 RSS를 사용했다. tracemalloc 자체도 메모리를 차지해 n=6,400,000에서 RSS가 268MB에서 491MB로 늘었기 때문에, 가장 큰 두 크기(51,200,000과 102,400,000)는 tracemalloc 없이만 측정했다.

## A1. 측정한 입력 크기

100,000 / 400,000 / 1,600,000 / 6,400,000 / 25,600,000 / 51,200,000 / 102,400,000의 7개 크기로 측정했다. 가장 큰 입력은 가장 작은 입력의 1,024배다. 스트림의 값 종류를 0.4n으로 제한했기 때문에, 실제로 서로 다른 값의 개수는 모든 크기에서 n의 약 36.7%였다.

## A2. 시간과 메모리 중 먼저 부담이 된 것

| n | set 시간 | FM 시간 | 프로세스 RSS |
|---|---|---|---|
| 100,000 | 0.09초 | 0.26초 | 22MB |
| 400,000 | 0.37초 | 0.96초 | 34MB |
| 1,600,000 | 1.32초 | 2.76초 | 79MB |
| 6,400,000 | 6.10초 | 11.70초 | 268MB |
| 25,600,000 | 26.29초 | 47.32초 | 890MB |
| 51,200,000 | 57.74초 | 95.82초 | 1,762MB |
| 102,400,000 | 119.85초 | 197.64초 | 3,507MB |

정확한 집계 방식은 n=51,200,000에서 약 58초, n=102,400,000에서 약 120초가 걸렸고, 마지막 크기의 RSS는 약 3.5GB였다. 시간이 길어지기는 했지만 해당 크기까지 처리가 끝났으며, n을 2배로 늘린 구간마다 RSS도 약 1.98\~1.99배 증가했다. 이 비율이 유지된다고 가정하면 n=204,800,000에서는 약 7.0GB가 필요해 측정 당시 가용 메모리 5.4GB를 넘는다. 같은 크기에서 시간은 약 240초로 예상되어 불편하지만 실행이 불가능한 수준은 아니므로, 다음 크기에서는 메모리가 먼저 제약이 될 것으로 판단했다. 다만 204,800,000은 직접 실행하지 않고 외삽한 값이며, 실제 메모리 부족 오류를 확인한 것은 아니다.

시간 면에서는 오히려 FM이 모든 크기에서 set보다 느렸다(102,400,000에서 197.64초 대 119.85초). FM은 원소마다 파이썬에서 blake2b 해시를 계산하기 때문이다. 즉 FM은 메모리를 아끼는 방법이지 시간을 아끼는 방법이 아니었다.

## A3. 입력 크기에 따른 메모리 변화

| n | 서로 다른 값 | set 메모리 | FM 메모리 | 서로 다른 값 하나당 set 메모리 |
|---|---|---|---|---|
| 100,000 | 36,702 | 3.93MB | 약 4.4KB | 107.0B |
| 400,000 | 146,970 | 11.59MB | 약 4.4KB | 78.9B |
| 1,600,000 | 587,625 | 46.65MB | 약 4.4KB | 79.4B |
| 6,400,000 | 2,349,909 | 188.29MB | 약 4.4KB | 80.1B |
| 25,600,000 | 9,399,592 | 756.42MB | 약 4.4KB | 80.5B |

set은 서로 다른 값을 직접 보관하므로 값 하나당 약 80바이트씩 메모리가 늘었다. FM은 64개 추정기의 최고 기록만 보관한다. FM을 사용하면 메모리를 크게 줄일 수 있는 대신, 서로 다른 값의 정확한 개수를 얻는 것은 포기해야 했다. 이 표의 메모리 값은 tracemalloc 값이므로 A2의 RSS와 같은 지표로 섞어 비교하지 않았다.

## A4. 두 방식의 메모리 증가율

| 구간 (n 4배) | set 메모리 | FM 메모리 |
|---|---|---|
| 100,000 → 400,000 | 2.95배 | 1.00배 |
| 400,000 → 1,600,000 | 4.02배 | 1.00배 |
| 1,600,000 → 6,400,000 | 4.04배 | 1.00배 |
| 6,400,000 → 25,600,000 | 4.02배 | 1.00배 |

set의 메모리는 n이 4배가 될 때마다 약 4배씩 늘어 n에 정비례했다. 첫 구간만 2.95배인 이유는 작은 크기에서 고정 비용이 섞여 값 하나당 메모리가 107.0B로 컸기 때문이며, 두 번째 구간부터는 약 80B로 수렴했다. FM은 모든 구간에서 1.00배였고, 측정 범위 전체에서 메모리가 4,432\~4,438바이트로 6바이트만 변했다. 이 차이는 데이터를 저장해서가 아니라 해시할 키 문자열이 길어진 만큼 생긴 것이다. FM의 메모리는 데이터의 양이 아니라 추정기 수(64개)가 정하기 때문에, 입력을 더 많이 읽어도 늘어나지 않는다.

## A5. FM의 정확도와 입력 크기의 관계

| n | 실제 개수 | FM 추정값 | 추정값 / 실제 개수 |
|---|---|---|---|
| 100,000 | 36,702 | 38,020 | 1.04 |
| 400,000 | 146,970 | 152,078 | 1.03 |
| 1,600,000 | 587,625 | 506,928 | 0.86 |
| 6,400,000 | 2,349,909 | 1,622,168 | 0.69 |
| 25,600,000 | 9,399,592 | 8,110,840 | 0.86 |
| 51,200,000 | 18,799,271 | 19,466,017 | 1.04 |
| 102,400,000 | 37,596,727 | 25,954,689 | 0.69 |

FM 추정값을 실제 개수로 나눈 비율은 0.69\~1.04였고 7개 크기 모두 2배 이내였지만, 입력이 커질수록 1에 가까워지는 추세는 없었다. FM의 상대오차는 입력 크기가 아니라 추정기 수와 조합 방식이 정하는데, 이번 실험에서는 추정기 수를 64개로 유지했으므로 입력이 커져도 정확도가 좋아질 이유가 없다. 또한 추정의 기본값인 2^R이 2의 거듭제곱 단위로만 바뀌므로 추정값이 n에 따라 매끄럽게 증가하지 않고, 실제 개수가 그 단위 사이 어디에 놓이는지에 따라 비율이 정해진다. 이것이 0.69, 0.86, 1.03\~1.04 근처의 비율이 반복된 이유다. 다만 이 세 값만 나오는 것이 모든 데이터에서 성립하는 FM의 일반적인 성질이라는 뜻은 아니다.

## A6. 측정 환경과 한계

| 항목 | 값 |
|---|---|
| CPU | Intel Core i7-1195G7 @ 2.90GHz, 4코어 8스레드 |
| 메모리 | WSL2에 할당된 7.6GB, 측정 당시 가용 메모리 약 5.4GB |
| 운영 환경 | WSL2 (Ubuntu), Python 3.12.3 |
| 같이 실행 중이던 프로그램 | VS Code, 크롬 탭 1개, 카카오톡 |
| 측정 당시 시스템 부하 (load average) | 0.66 / 0.92 / 0.74 |

7.6GB는 WSL2에 할당된 메모리이며, PC 전체의 물리 RAM은 16GB로 별도다. 실행 시간은 위 환경에서 한 번씩 측정한 값이므로, 다른 실행이나 다른 컴퓨터에서 똑같이 나온다고 볼 수는 없다.
