# Week 4 — 데이터 스트림 마이닝

## 1. 과제 개요

이번 과제에서는 메모리에 전부 담기 어렵고 한 번만 읽을 수 있는 데이터 스트림을 다뤘다. Bloom filter, Flajolet-Martin(FM), Reservoir sampling으로 전체 데이터를 저장하는 대신 필요한 정보만 남겼다. 세 방법 모두 정확한 원본 정보를 보존하는 것을 포기하고, 정해 둔 크기의 메모리로 한 번만 훑는 처리를 구현했다.

## 2. Task별 구현

### Task 1 — 세 가지 스케치 (`task1_sketches.py`)

**Bloom filter**

원소가 들어 있는지 적은 메모리로 확인하기 위해 Bloom filter를 구현했다. 비트 m개를 bytearray에 8개씩 묶어 저장하고, 해시 k개가 가리키는 위치를 1로만 바꾸도록 했다. 거짓 양성률은 예측 0.860%, 측정 0.840%였으며, 삽입한 원소를 없다고 판단하는 거짓 음성은 0개였다.

**Flajolet-Martin**

서로 다른 원소 수를 추정하기 위해 해시값 뒤쪽의 연속된 0 개수 중 최댓값 R을 기록하고, 2^R을 추정의 바탕으로 사용했다. 64개 추정기의 결과를 그룹 안에서는 중앙값으로, 그룹 사이에서는 평균으로 합쳤다. 같은 원소가 다시 들어와도 같은 해시값이 나오므로 해당 기록을 더 키우지 않으며, 채점용 스트림의 추정값은 실제 개수의 0.79배였다.

**Reservoir sampling**

전체 길이를 모르는 스트림에서 크기 k의 표본을 뽑기 위해 처음 k개를 담고, 이후에는 기존 원소 하나를 확률적으로 교체했다. i를 0부터 셀 때 새 원소의 채택 확률은 k / (i + 1)이다. 난수는 함수에 전달된 seed로 만들어, 같은 seed에서는 같은 표본이 재현되고 seed가 다르면 다른 표본이 나오도록 했다. 서로 다른 seed로 4,000번 시행한 검증에서 편차는 8.9%로, 기준인 15% 미만을 만족했다.

FM과 Reservoir는 제너레이터를 받을 수 있도록 입력을 리스트로 바꾸거나 len()으로 길이를 구하지 않고 처리했다. Task 1의 `--verify` 검사 4개는 모두 통과했다.

### Task 2 — 정확한 집계의 한계 측정 (`task2_limits.py`)

set과 FM으로 서로 다른 원소 수를 세고, 입력 100,000~102,400,000의 7개 크기에서 시간과 메모리를 비교했다. set의 메모리는 입력이 4배가 될 때마다 약 4배씩 늘어 입력 크기에 비례했지만, FM은 약 4.4KB를 유지했다. 실측한 최대 크기까지는 처리가 끝났으나 다음 크기의 메모리를 외삽하면 가용량을 넘어서, 더 큰 입력에서는 메모리가 먼저 제약이 될 것으로 판단했다. 반면 FM의 실행 시간은 set보다 길었으므로, 이번 구현의 이점은 속도보다 메모리 절약에 있었다. 측정 도구의 영향을 구분하려고 시간과 메모리를 따로 측정하도록 스크립트를 수정했으며, 자세한 수치와 외삽 근거는 limits.md에 정리했다.

### Task 3 — 같은 메모리로 오류 줄이기 (`task3_budget.py`)

80,000비트 예산에서 해시 개수를 기본 필터의 1개에서 7개로 늘렸다. 7을 직접 고정하지 않고 `round((비트 수 / 예상 아이템 수) * ln(2))`로 계산해, 예산이나 예상 원소 수가 달라져도 설정이 따라 바뀌도록 했다. 거짓 양성률은 9.511%에서 0.860%로 약 91.0% 감소했고, strong 등급을 받았다. `memory_bits()`는 실제 비트 배열의 용량을 보고하도록 했으며, 삽입 수를 10배로 늘려도 배열의 메모리는 늘어나지 않았다. 대신 원소마다 계산하고 확인해야 하는 해시 위치가 많아졌으며, 삽입 수가 예상보다 늘면 같은 정확도를 보장하지 못한다.

## 3. 설계에서 내린 결정

### 1) 비트 8개를 한 바이트에 저장했다

80,000비트를 10,000바이트의 bytearray에 담아 비트 배열의 저장 공간을 예산에 맞췄다. 기본 NaiveFilter는 위치 하나에 1바이트를 쓰므로, 80,000비트라는 보고값과 달리 배열 데이터에만 그 8배의 공간을 사용하고 있었다. 비트를 묶으면 공간을 줄일 수 있지만, 값을 읽고 쓰는 코드가 복잡해지는 대가가 있었다. `idx >> 3`은 몇 번째 바이트인지, `idx & 7`은 그 바이트 안의 몇 번째 비트인지를 구하는 데 사용했다.

### 2) FM에서는 원소당 해시를 한 번만 계산했다

1억 개가 넘는 입력에서 원소마다 해시를 64번 계산하는 부담을 줄이기 위해, 해시값의 하위 6비트로 64개 추정기 중 하나를 골라 갱신했다. 대신 각 추정기는 원소가 균등하게 나뉜다고 가정할 때 전체 스트림의 약 1/64만 보므로, 최종 추정에 64를 곱해 전체 규모로 환산했다. 따라서 전체 입력에 64개 해시 함수를 각각 적용하는 교재 방식과는 다르며, 계산량을 줄이는 대신 추정기마다 관측하는 데이터가 줄어드는 선택을 했다.

### 3) 시간과 메모리를 별도로 측정했다

tracemalloc을 켜면 실행 시간이 약 4배 늘어나(n=100,000에서 0.09초 → 0.34초), 한 번의 실행에서 얻은 시간과 메모리를 그대로 비교하기 어려웠다. 그래서 `task2_limits.py`에 추적을 끄는 옵션과 RSS 측정을 추가하고, `limits.json`의 `traced` 필드로 측정 조건을 구분했다. 측정 도구의 영향을 줄이는 대신 같은 크기를 시간용과 메모리용으로 나누어 실행해야 했다. 수정 금지 파일은 Task 3의 채점기인 `bench.py`뿐임을 확인했고, 이 파일은 변경하지 않았다.

## 4. 어려웠던 점과 이해한 과정

FM의 결과를 해석할 때는 메모리를 줄였다는 사실과 실행 속도를 구분할 필요가 있었다. 메모리는 약 4.4KB로 유지됐지만 시간은 set보다 더 걸리는 결과를 통해, 근사 알고리즘이라고 해서 모든 자원을 적게 쓰는 것은 아니라는 점을 이해했다. 이번 구현은 정확한 개수를 포기하고 메모리를 아낀 것이며, 속도는 별도로 측정해 판단해야 했다.

FM의 조합 규칙은 교재의 그룹 안 평균 → 그룹 간 중앙값 방식과 순서를 뒤집은 방식을 비교했다. 이번 실험에서는 중앙값을 먼저 구한 쪽이 더 안정적이었고, 평균이 큰 추정값의 영향을 받는다는 점을 결과와 연결해 이해했다. 다만 이것을 항상 더 좋은 규칙이라는 결론으로 확대하지 않고, 이번 데이터에서 측정한 결과에 따른 선택으로 정리했다.

## 5. AI 사용

VS Code에서 Claude를 사용해 과제 파일 분석, 코드 구현, 측정 실행을 진행했다. limits.md, observation.md, README.md는 내가 초안을 쓴 뒤, Claude의 도움을 받아 내용 구성과 문장, 숫자 누락을 검토했다.

문서의 숫자는 VS Code의 Claude로 limits.json, bench.txt 등 원자료와 대조해 확인했다. 검토 과정에서 실제로 실행한 크기와 외삽한 크기를 구분했고, 한 번만 읽는 스트림을 다시 읽어 필터를 재구축할 수 있다고 가정한 설명을 스트림의 전제에 맞게 고쳤다. AI가 만든 내용이라도 채점 결과와 원자료에 맞는지, 사용한 코드와 숫자를 직접 설명할 수 있는지를 제출 전 확인 기준으로 삼았다.
