## Task 3 · 같은 메모리, 더 적은 실수

### Q8. 바꾼 파라미터와 유도

바꾼 것: 해시 개수 `k` 를 1 개(NaiveFilter) → **7 개**. 비트는 동일하게 80,000.

유도 단계:

    FP(k) = (1 - e^(-kn/m))^k
    p = e^(-kn/m)  치환  →  k = -(m/n)·ln p,   FP = (1-p)^k
    ln FP = k·ln(1-p) = -(m/n)·ln(p)·ln(1-p)
    m/n 은 상수 → ln(p)·ln(1-p) 를 최대화
    d/dp[ln p·ln(1-p)] = ln(1-p)/p - ln(p)/(1-p) = 0
    이 식은 p ↔ 1-p 대칭 → 최댓값은 p = 1/2
      확인: p=1/2 에서 양변 모두 2·ln(1/2) = -1.3863
    p = 1/2 → e^(-kn/m) = 1/2 → kn/m = ln 2

    k* = (m/n)·ln 2 = 10 × 0.693147 = 6.93 → 7

코드는 상수 7 을 박지 않고 `round((n_bits / EXPECTED_ITEMS) * math.log(2))`
로 계산한다 (`task3_budget.py`).

`p = 1/2` 의 의미 = '비트의 정확히 절반이 켜졌을 때 최적'.
실측 비트 점유율 **50.45%** (40,359 / 80,000) 로 확인됨.

### A4 · 두 증가율 (n 을 4 배 할 때)

| 구간 | set 메모리 | FM 메모리 | set 시간 |
|---|---|---|---|
| 100,000 → 400,000 | 2.95x | 1.00x | 4.29x |
| 400,000 → 1,600,000 | 4.02x | 1.00x | 3.60x |
| 1,600,000 → 6,400,000 | 4.04x | 1.00x | 4.61x |
| 6,400,000 → 25,600,000 | 4.02x | 1.00x | 4.31x |

- **set 메모리: n 에 정비례 (4 배 → 4.02x).** distinct 당 약 80 바이트로 일정.
  첫 구간만 2.95x 인 이유는 n=100,000 의 distinct 당 107 B 에 작은 크기의
  고정 오버헤드가 섞여 있기 때문. 두 번째 구간부터 78.9 → 79.4 → 80.1 → 80.5 B
  로 수렴한다.
- **FM 메모리: 1.00x. 완전히 평평하다.** FM 이 들고 있는 것은 버킷 64 개의
  정수 배열뿐이고, 그 크기는 `n_hashes`(64) 가 정한다. 데이터는 크기에
  기여하지 않는다.
- set 시간도 n 에 정비례 (4 배 → 3.6~4.6x). 즉 정확한 방식은 시간도 메모리도
  선형이고, 문제는 메모리의 **절대량**이다.

set 메모리를 n 에 대한 식으로: 약 80 B × 0.367n = **n 당 약 29.4 바이트**.

**무엇이 먼저 바닥났는가 → 메모리**

근거: RSS 가 n 에 정비례한다 (6.4M→25.6M→51.2M→102.4M 에서 268→890→1762→3507 MB,
2 배당 1.98~1.99x). 다음 단계인 n=204,800,000 을 외삽하면

    RSS 필요량  ≈ 3,507 MB × 2 = 약 7.0 GB
    가용 메모리 = 5.4 GB  (WSL2 에 할당된 7.6 GB 중)
    시간        ≈ 240 초 (4 분) — 불쾌하지만 치명적이지는 않다

즉 시간은 "짜증나는" 수준으로 완만하게 나빠지는데 메모리는 **벽에 부딪힌다**.
204.8M 은 실제로 시도하지 않았다 (OOM 또는 스왑 스래싱으로 다른 작업까지
영향을 받을 수 있어 의도적으로 멈춤). 선형성이 4 개 구간에서 1.98~1.99x 로
일관되므로 외삽의 근거는 충분하다.

FM 쪽은 같은 n=102.4M 에서 메모리가 여전히 4.4 KB 다. FM 은 이 기계에서
메모리로 멈추는 지점이 없다 — 멈춘다면 시간 때문이다 (197.64 초).

### A5 · FM 정확도 비율

| n | 정답 distinct | FM 추정 | 비율 | 오차 |
|---|---|---|---|---|
| 100,000 | 36,702 | 38,020 | 1.04x | 3.6% |
| 400,000 | 146,970 | 152,078 | 1.03x | 3.5% |
| 1,600,000 | 587,625 | 506,928 | 0.86x | 13.7% |
| 6,400,000 | 2,349,909 | 1,622,168 | 0.69x | 31.0% |
| 25,600,000 | 9,399,592 | 8,110,840 | 0.86x | 13.7% |
| 51,200,000 | 18,799,271 | 19,466,017 | 1.04x | 3.5% |
| 102,400,000 | 37,596,727 | 25,954,689 | 0.69x | 31.0% |

최소 0.69x, 최대 1.04x, 평균 0.89x. **7 개 전부 2 배 이내.**

**n 이 커지면 좋아지는가 나빠지는가 → 둘 다 아니다.** 오차가 3.5% → 13.7% →
31.0% → 13.7% → 3.5% → 31.0% 으로 **오르내린다.** 추세가 없다.

이유: FM 의 상대 오차는 n 이 아니라 **추정기 개수(64)** 가 정한다. n 이 커져도
추정기가 늘지 않으므로 정확도가 개선될 이유가 없다. 오르내리는 패턴은 추정치가
`2^R` 의 조합이라서 값이 2 의 거듭제곱 격자에 걸리기 때문이다 — 정답이 격자
눈금 사이 어디에 떨어지는지에 따라 비율이 순환한다. 실제로 0.69 / 0.86 / 1.04
세 값만 반복해서 나타난다.

정확도를 높이려면 추정기를 늘려야 하고 (메모리가 그만큼 늘고), 그 방향의
끝에 HyperLogLog 가 있다.
