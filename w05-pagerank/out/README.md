## 2. Task별 구현

### Task 1 — 막다른 길과 거미 덫 처리

막다른 길은 나가는 링크가 없어 점수를 다음 노드로 보내지 못하는 경우이고, 거미 덫은 들어간 점수가 특정 노드 집합 안에서만 도는 경우다.
망가진 버전의 막다른 길 예제에서는 전체 점수의 합이 3번의 반복 만에 1에서 0이 되어, 점수가 실제로 사라지는 것을 확인했다.

막다른 길 처리 방법 4가지 중에서는 그곳에 모인 점수를 모든 노드에 균등하게 재분배하는 방법을 선택했다.
노드를 제거하지 않고 전체 점수를 보존할 수 있고, Task 3의 DenseMatrix도 같은 방식을 사용하므로 결과를 1e-9 이내로 비교하기에 적합했다.
대신 재분배 대상에 막다른 길 자신도 포함되므로, 나누어 주는 점수의 1/n 몫을 다시 받는다.

거미 덫은 확률 1−beta로 전체 노드 중 하나를 균등하게 선택하는 텔레포트를 넣어 빠져나갈 수 있게 했다.
막다른 길 재분배와 텔레포트는 출발 이유는 다르지만, 둘 다 모든 노드에 같은 값을 더하므로 하나의 base로 묶을 수 있었다.
beta=0.85인 거미 덫 예제에서 들어오는 링크가 없는 A의 점수가 0.0375=0.15/4인 것을 통해 텔레포트 항의 의미를 확인했다.

### Task 2 — 수렴 횟수와 실행 시간 측정

beta는 0.5, 0.6, 0.7, 0.8, 0.85, 0.9, 0.95, 0.99의 8개 값을 사용했고, 그래프 크기는 1,200개, 6,000개, 20,000개로 비교했다.
tol은 1e-2, 1e-6, 1e-10으로 바꾸어 정밀도를 높일 때 필요한 반복도 확인했다. 여러 조건으로 기록한 측정 결과는 총 40행이었다.

n=1,200, tol=1e-10에서 beta가 0.5에서 0.99로 커질 때 반복 횟수는 14번에서 24번으로 늘었다.
beta가 1에 가까워지면 반복 횟수가 급격히 늘어날 것이라는 예상과 달리, 이번 그래프에서는 비교적 완만하게 증가했다.
반복 후반의 변화량 감소 비율을 beta로 나누면 약 0.43이어서, beta뿐 아니라 그래프 자체의 링크 구조도 수렴에 영향을 준다고 이해했다.

시간은 한 번 측정한 값만으로 비교하면 실행 순서나 당시 환경에 따라 흔들릴 수 있어, beta=0.85, tol=1e-10에서 각 크기를 3회씩 측정한 중앙값을 따로 구했다.
반복 횟수는 20번, 22번, 21번으로 비슷했지만, 시간은 0.0138초에서 0.3792초로 증가했다.
top-10 순위도 비교했으며, n=1,200에서는 beta=0.5와 0.6 사이에서 7·8위가 바뀌었다. 자세한 표와 해석은 `convergence.md`에 정리했다.

### Task 3 — 행렬 없이 PageRank 계산

n×n 크기의 행렬 M을 저장하는 대신, 현재 점수 r과 다음 점수 nr을 담는 두 배열을 사용했다.
실제로 존재하는 간선을 따라 점수를 전달하고, 링크마다 필요한 분배 비율은 해당 노드의 링크 개수로 계산하도록 했다.
따라서 점수 배열에 저장하는 float 수는 2n이며, 간선 수 m에 비례하는 float 배열은 따로 두지 않았다. 그래프의 인접 리스트 저장 공간은 이 계산과 별도다.

구현 과정에서 중간값을 담는 s 배열까지 따로 두면 길이 n인 배열이 3개가 되어 3n이 된다는 문제를 발견했다.
s를 별도로 만들지 않고 기존 공간에서 필요한 계산을 처리하는 제자리 방식으로 바꾸어, 점수 배열을 r과 nr 두 개로 맞췄다.
n=1,200에서 저장하는 float는 2,400개로, dense 행렬의 1,440,000개와 비교하면 600배 적었다.

bench.txt 기준 실행 속도는 dense 대비 55.2배 빨랐으며, strong 등급을 받았다.
dense 결과와의 노드별 최대 차이는 5.55e-17로, 비교 기준인 1e-9보다 충분히 작았다.

## 3. 설계에서 내린 결정

### 1) beta 설정과 망가진 구현을 구분했다

Task 1의 R6에서 주의할 점은 올바른 구현의 beta만 1로 바꾼다고 두 결함을 모두 재현할 수 있는 것은 아니라는 점이었다.
beta=1은 텔레포트 확률을 0으로 만드는 설정이지만, 막다른 길의 점수를 재분배하는 처리까지 없애지는 않는다.
따라서 재분배가 남아 있으면 막다른 길에서도 전체 점수가 보존되며, 점수가 사라지는 망가진 버전과는 동작이 다르다.
망가진 버전과 수정한 버전을 비교할 때는 beta 값뿐 아니라, 갱신 과정에 재분배와 텔레포트가 각각 들어 있는지를 구분해야 한다고 이해했다.

### 2) 행렬을 없앤 뒤에도 중간 배열을 확인했다

큰 행렬을 없앴다고 메모리 조건까지 자동으로 만족하는 것은 아니었다.
r, nr 외에 s를 하나 더 두면 점수 배열의 float 수가 2n에서 3n으로 50% 늘어나므로, 계산 중 잠깐 쓰는 배열도 저장 공간에 포함해야 했다.
필요한 중간값을 별도 배열에 모두 보관하지 않는 방식으로 바꾸면서, 같은 계산도 값을 언제 만들고 어디에 두는지에 따라 메모리가 달라진다는 점을 알게 되었다.

텔레포트 항도 (1−beta)/n이라는 같은 값을 모든 노드에 적용하므로, 한 번 계산한 값을 재사용하면 된다.
n개의 점수를 갱신하는 것은 필요하지만, 같은 값을 n×n개 저장할 필요는 없었다. 이 설명은 `observation.md`의 R5 항목에 정리했다.

### 3) 반복 횟수와 실행 시간을 따로 비교했다

반복 횟수는 수렴 조건에 도달하기까지 점수를 몇 번 갱신하는지를 나타내고, 실행 시간은 갱신 한 번에 처리할 작업량에도 영향을 받는다.
노드 수가 약 16.7배가 되어도 반복 횟수는 20~22번으로 비슷했지만, 처리할 노드와 간선이 많아져 전체 시간은 약 27.5배 늘었다.
그래서 크기별 비교에서는 두 항목을 나누어 설명하고, 시간은 3회 측정의 중앙값을 사용했다.

최대 반복 횟수인 500번에 도달한 측정 행은 없었으며, `test_tasks.py`에서 실행된 테스트 8개는 모두 통과했다.
다만 텔레포트에 dense 연산이 필요 없는 이유를 설명하는 R5는 자동 테스트에서 SKIP되는 항목이므로, 테스트 통과와 별도로 문서에 근거를 적었다.

## 5. 어려웠던 점과 이해한 과정

가장 크게 배운 것은 beta만으로 실제 수렴 속도를 판단할 수 없다는 점이다.
처음에는 beta가 1에 가까워질수록 느려진다는 설명에 집중했지만, 실제로는 그래프에서 점수가 얼마나 잘 섞이는지도 함께 보아야 했다.
이번에는 beta=0.99에서도 반복 후반의 변화량이 약 0.43배씩 줄어 24번에 끝났다.
따라서 beta가 1에 가까울 때 매우 느려질 수 있다는 경고를, 모든 그래프에서 반복 횟수가 폭증한다는 뜻으로 받아들이면 안 된다고 이해했다.

또한 같은 수학적 계산을 한다고 해서 같은 자료구조가 필요한 것은 아니라는 점을 배웠다.
dense 행렬이 표현하던 링크 전달과 균등 분배를 간선 순회와 두 점수 배열로 계산해도, 결과 차이는 5.55e-17에 그쳤다.
그 작은 차이는 덧셈 순서와 나눗셈 형태에 따른 부동소수점 반올림으로 설명할 수 있었으며, 메모리를 줄였기 때문에 정확도를 그만큼 포기한 것은 아니었다.

확인하지 못한 부분도 있다.
작은 그래프와 큰 그래프를 비교했을 때 간선 수는 약 17.3배 늘었지만 실행 시간은 약 27.5배 늘었다.
반복 횟수까지 반영한 간선 방문 횟수도 약 18.2배이므로, 이 차이를 간선 수 증가만으로 설명할 수는 없었다.
메모리 접근이나 실행 환경이 영향을 주었을 가능성은 있지만, 별도의 측정으로 원인을 구분하지 못했기 때문에 특정 원인으로 단정하지 않았다.
